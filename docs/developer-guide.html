Developer Guide

How to run this project locally, how it talks to Contentful, what it depends on, the decisions behind its architecture, and how to contribute a change.

Overview

dan.moi is a single-page personal site built entirely with vanilla JavaScript and native Web Components — no framework, no bundler, and no build step. Four dropdown panels (Blog, Writes Code, Makes Music, and Collects Moods) each follow the same two-pane pattern, a list view that opens into a detail view, and all of their content comes from Contentful over GraphQL.

The rest of this guide covers how to run the project, how it talks to Contentful, what it depends on, the reasoning behind its main architectural choices, and how to contribute a change.

Running the App Locally

To run the site on a local machine, follow these steps:

  1. Copy .env.example to .env and fill in a Contentful space ID and access token.
  2. Run node serve.mjs from the project root.
  3. Open http://localhost:3333 in a browser.

Set the PORT environment variable to serve on a different port, for example PORT=1234 node serve.mjs. The server reads .env and exposes the Contentful credentials to the browser at runtime — nothing is baked in at build time, because there is no build step.

Jumping straight into a panel

Append one of these query parameters to any URL, including a direct article link, to open a panel automatically during development:

  • ?dev-mode=blog-list — Blog panel opens and stays open
  • ?dev-mode=blog-article — Blog panel opens with the first article loaded
  • ?dev-mode=code-list — Writes Code panel opens and stays open
  • ?dev-mode=code-project — Writes Code panel opens with the first project loaded
  • ?dev-mode=music-list — Makes Music panel opens and stays open
  • ?dev-mode=moodboard — Collects Moods panel opens and stays open

How It Fetches from Contentful

All content comes from Contentful’s GraphQL Content API. js/contentful-graphql.js sends requests directly to https://graphql.contentful.com/content/v1/spaces/<space-id>/environments/master with fetch, authenticated by a bearer token — the project depends on no Contentful SDK.

Every fetch function returns a { data, errors } tuple instead of throwing, so the calling panel decides how to handle a failed request rather than needing a try/catch around every call.

The Contentful GraphQL API caps a single collection query at 100 items, so contentful-graphql.js pages through larger collections with a skip argument. The blog and moodboard panels drive that pagination with an IntersectionObserver that requests the next page as the reader scrolls near the bottom of the list.

Rich text fields render through a local implementation in js/contentful-rich-text-html.js rather than a CDN-hosted renderer, removing a runtime dependency on an external script for content that every blog post and code project article depends on.

Credentials never ship in the repository. In development, serve.mjs reads .env and exposes it to the browser through a /contentful-env.js endpoint as window.CONTENTFUL_CONFIG. In production, netlify/functions/contentful-env.js serves the same shape from Netlify’s own environment variables.

Key Dependencies

The project has no package.json and installs no npm packages. Every script in js/ runs unmodified in the browser, so the dependencies below are services and assets, not libraries.

Contentful GraphQL Content API All panel content (blog posts, code projects, music projects, moodboard entries) Queried directly with fetch; no Contentful SDK
Roboto Mono (Google Fonts) UI and label typography (.type-ui, .type-label) The only external stylesheet the site loads

Key Technical Decisions

A few decisions shape most of the codebase. Each is described here with the reasoning behind it.

Vanilla web components, no framework

Every panel and reusable primitive is a native Custom Element, not a React, Vue, or Svelte component. The project trades a component framework’s conveniences for zero build step and zero runtime dependency: node serve.mjs needs no compile stage, and any browser can load index.html directly.

CSS custom-property design tokens

css/reset.css defines the site’s color palette as CSS custom properties (--color-*), and every panel and component reads from that token set instead of hardcoding colors. A later refactor added semantic per-panel tokens, such as --color-panel-blog-bg, so each of the four panels’ trigger, background, and focus-ring colors are named by role rather than by raw hue.

A utility-class system over component CSS

css/css-utils.css provides a small, Tailwind-style set of single-purpose classes for layout, spacing, and typography, composed directly in HTML. A component stylesheet only adds a rule when no utility covers the need: a unique value, a complex selector, or a property no utility exposes.

CSS bundled and minified at request time, not at build time

index.html loads a single /css/bundle.css. netlify/functions/css-bundle.js and its development equivalent in serve.mjs concatenate and minify the files listed in CSS_BUNDLE_FILES on every request, trading a small amount of per-request server work for keeping the project’s zero-build-step constraint.

Dark mode is opt-in only

The site does not follow the visitor’s prefers-color-scheme automatically. A first-time visitor always sees light mode’s full-color branding; dark mode is only reached through the explicit toggle in theme-toggle.js, and that choice then persists in localStorage. This is a deliberate product decision documented directly in theme-init.js, not an oversight.

Rich text rendered locally, not from a CDN

Contentful rich text fields were originally rendered through a CDN-hosted ESM import. js/contentful-rich-text-html.js now implements that rendering locally, removing a runtime dependency on an external script for content every blog post and code project article depends on.

A design-system audit skill runs against the codebase periodically

.claude/skills/design-system-ops/ is a Claude Code skill that audits the project’s tokens, typography, and accessibility for drift. Its diagnostics have already driven fixes to focus-ring contrast, token naming, and typography-scale conformance — see the change log for the most recent pass.

Contributing

The project’s git history shows a consistent branching pattern: feature and fix work happens on a branch off develop, named for what it does (feat/..., fix/..., or refactor-N), and merges into develop through a pull request. A separate pull request from develop into main acts as a release, bundling everything develop has accumulated since the last one.

To propose a change:

  1. Branch from develop, using a feat/, fix/, or refactor- prefix that describes the change.
  2. Load the /css skill before writing or editing any HTML or CSS. It documents the full utility class reference and the rules this project enforces — no px units outside hairline borders, no inline styles, unitless line-height, and more.
  3. Run node serve.mjs and check the change in a real browser. The project has no automated test suite; a browser check on the target devices is the verification step.
  4. Open a pull request into develop.

Target devices are a MacBook Pro (desktop Safari and Chrome) and an iPhone (iOS Safari) — there is no Android or other mobile browser to support.
